The 90-second version
  1. “You paste one link. Code validates it, pulls the page, and finds the seven ticket IDs with a regex — no model yet, because an ID has to be exact.”
  2. “The first agent reads the page for the things a regex can’t do: the version and the deploy dates written in prose.”
  3. “Then one agent call per ticket. Seven in, three customer-facing, four internal. That filter used to be somebody’s afternoon.”
  4. “Three doc pages get written into a fixed nine-section template, and one email that groups by type of change instead of by ticket.”
  5. “Now the part worth seeing: a separate reviewer agent reads the drafts against the source tickets. It caught a value range the writer got wrong and a date the docs and email disagreed on.”
  6. “Both flags land on a person’s screen with the draft. They fix them, they approve — and only then does it publish, to internal recipients only.”
  7. “So you don’t trust the model. You trust the system around it.”
Worked example is illustrative — REL-4821, the ticket keys and the field names are invented for demonstration; the stages, prompts and controls are the real operating pattern, abstracted.

What an enterprise actually watches — four layers

Classic observability asks “is it up?” Agent observability adds three more questions, each with a different owner. Miss a layer and someone’s question has no answer.

◆ The one number to put on a wall

Human edit rate. When reviewers stop fixing things, the system is earning trust; when it spikes, something upstream changed — a model update, a new team writing tickets differently — and it spikes before a customer ever sees the problem. It’s also your free eval signal: the gap between “judge said fine” and “human still fixed it” is exactly the backlog you work down. One caveat: pair it with random audit samples, or it quietly teaches people to rubber-stamp.

In one breath

“Four layers, four owners: ops tells you it’s alive, quality tells you it’s drifting, safety tells you it’s contained, outcome tells you it’s worth it. The metric I’d wire an alert to is human edit rate — it moves before anything customer-facing breaks, and every edit is a free labeled example for the next eval.”

◆ The week-7 spike is the whole argument

The model vendor shipped an upgrade under the pipeline. Flag rate and edit rate both jumped that week — because every run is stamped with its prompt-set and model version, one glance separated “our inputs changed” from “the model changed underneath us.” Rolled the model pin back, re-ran the golden set against the new version, shipped it properly the week after. Without the version stamp, that’s a month of “it feels worse lately.” Drift has exactly two sources — your inputs change, or your model does — and the stamp is what tells them apart.

4

When loops arrive — observing real agency

This pipeline has a fixed shape, so you can read the code to know what happened. The moment an agent chooses its own next step — a loop, not a pipeline — the trace becomes the only ground truth. That’s why observability is a prerequisite for autonomy, not a follow-up.

  • Steps per task, against a step budget. A loop that usually finishes in 6 steps and suddenly takes 19 is telling you something no error log will.
  • Termination reason, as a first-class field. Goal reached · budget hit · stuck. The ratio of those three is the health of the loop; “budget hit” trending up means the task or the tools changed.
  • Tool-call error and retry rates, per tool. Loops hide flaky tools by retrying around them — invisible in output quality, obvious in the trace, and it’s where the cost goes.
  • Cost ceiling and kill-switch per task. A runaway loop is a bounded incident, not an open one — the same instinct as the allow-list, applied to spend.
  • Escalation rate. What fraction of tasks the loop hands to a human. Zero is as suspicious as fifty percent — it means the loop stopped knowing when it’s out of its depth.
◆ The principle

“A pipeline earns autonomy in stages: every span it logs today is the evidence that lets you loosen the control flow tomorrow. You don’t start with a free agent and add monitoring — you start with a monitored workflow and add freedom.”

5

Agent evaluation — and how a change actually ships

A prompt edit or a model swap changes behavior exactly like a code change — so it ships down the same road: versioned, tested against a fixed bar, rolled out gradually, rolled back by pin. Call it a release studio for prompts.

  1. Golden set — the fixed bar. ~30 past runs with the human-approved outputs as ground truth, plus planted-failure cases: a fabricated value the judge must flag, an injection attempt the pipeline must ignore. Real inputs, not synthetic ones — the golden set is the product’s memory of what “right” looks like.
  2. Offline eval in CI. Every prompt or model change re-runs the golden set before merge. Score agreement with the approved outputs; score the judge’s verdicts against the planted failures. A regression blocks the merge exactly like a failing unit test — no meeting, no vibes.
  3. Shadow. The new version runs beside the old on live releases, ships nothing, and its outputs are diffed and judged. Non-determinism is why this step exists: you’re measuring the distribution, not one lucky output.
  4. Canary. 10% of runs, gated on the two SLOs that matter: judge flag rate and human edit rate. Reviewers at the gate are your canary detectors, and they’re already looking.
  5. Rollout, pinned. Every run stamps its prompt-set + model version (section 1), so rollback is changing a pin — and the week-7 story in section 3 is this machinery paying for itself.
◆ The flywheel — the part that matters most

Every human edit at the gate is a free labeled example: the reviewer’s correction is the ground truth, and it flows straight into the golden set. The human gate isn’t just a safety control — it’s the data engine that makes next month’s pipeline better than this month’s. Most teams bolt evals on after; wiring the gate to feed them is the difference between having a review step and having a learning loop.

🎯 If asked “how would you evaluate agents at scale?”

“Same road code takes. A golden set of human-approved runs plus planted failures, re-run in CI on every prompt or model change; then shadow, then a canary gated on flag rate and edit rate; rollback is a version pin. And the golden set grows itself — every correction a reviewer makes at the gate becomes tomorrow’s eval case.”

Hard questions

Q“How would you know if this degrades six months from now?”
Trend the quality layer per version stamp — judge flag rate and human edit rate, alarmed on deviation. Drift has two sources, inputs or model, and the stamp tells them apart in one glance. → §3
Q“How do you evaluate something non-deterministic?”
Never on one output — on the distribution. Agreement with human-approved goldens across the whole set, shadow diffs on live traffic, and SLOs on rates rather than instances. One weird output is noise; a moved rate is a signal. → §5
Q“The judge grades the pipeline, evals grade the judge — isn’t that circular?”
Humans are the anchor. The golden outputs are human-approved, the planted failures are human-authored, and the edit rate is a human acting. Model grades model, but every chain terminates at a person on the record.
Q“What would you build first?”
The trace and the version stamp — before any new capability. You can’t gate, canary, audit, or roll back what you can’t see and can’t pin. Observability is the substrate every other control stands on. → §1
Q“Isn’t this heavy for a comms tool?”
The meter is sized to the blast radius, and most of it is a by-product — the multi-agent split already emits one clean span per agent. The point isn’t this pipeline; it’s that the same meter is what lets an enterprise say yes to the next twenty.

Why observability is the whole game

Most people can describe an agent. Some can describe guardrails. Almost none bring the operating model: what you watch after go-live, who watches each layer, how drift is caught, and how a prompt change ships behind an eval gate with a rollback pin. That’s the difference between “I built a demo” and “I know how to run this in production.”
