Act one · the enterprise system

A release-communications pipeline, built and deployed

A release page goes in. Customer-facing documentation and a notification to the client-facing teams come out. Four narrow model steps, one human gate, and a single scoped tool with permission to send anything.

Why four steps instead of one call

  • Focus. A prompt with one job hallucinates less than a prompt carrying four.
  • Output shape. A parse, a label, a document and a formatted message can't share one schema. The notification uses a delimiter format rather than JSON, because escaping HTML inside JSON is brittle — each step gets the contract that fits its payload.
  • Fan-out. Classification runs per ticket and drafting per document, in parallel. A monolith can't.
  • Localised failure. When the output is wrong you can see which step was wrong.
  • The seam. A single call has nowhere to put a human.

The design decision I'd defend hardest

It is deliberately not autonomous. My code decides the sequence; the model reasons inside each step and never chooses what runs next. This runs close to a production release, so predictability was worth more than flexibility. Autonomy earns its place where the path can't be enumerated — support triage, a coding agent. Publishing a release note isn't that shape.

The seam

The human gate, and the metric hiding inside it

A gate is not an eval, and conflating the two is how teams feel safe while flying blind.

A gate catches errors one at a time on the way out. An eval tells you whether version N+1 is better or worse than version N. I had the first and not the second, which meant that when I changed a prompt, I had no way of knowing whether I'd quietly broken something that used to work.

What I'd build first, and it costs almost nothing: capture the diff between what the model produced and what the human published. That gives two things at once — a regression set that builds itself from real production inputs, and edit rate as an online metric that falls as the system improves. Edit rate is also the answer to "when do you remove the human": by class of output, once it has been low and stable long enough to trust, and never all at once.

Act two · the system where I owned the whole quality problem

Four kinds of test, matched to four kinds of mistake

On my own editorial pipeline there was no reviewer but me, so the checking had to be built rather than staffed. The organising rule I wrote for it:

Where to put the accuracy target

"How accurate is it" is the wrong question — accurate at what, and what does an error there cost? I made the same call twice in unrelated domains. On a document-processing platform in a regulated healthcare setting, the confidence threshold routed low-confidence extractions to a human, biased toward precision because auto-filing a wrong authorisation is worse than making a person look at more documents. On the editorial pipeline, one classification dimension is a hard gate because getting it wrong breaks the output, and a second is reported only because getting it wrong changes nothing.

One instance is an anecdote. Two is a way of working.

Judging what a rule can't check

Some output has no single right answer, and the honest response isn't to give up on measuring it — it's to layer cheap checks ahead of expensive judgement so the costly step only sees what survived.

Expect the pushback, and take it seriously

"Isn't a model judge just marking its own homework?" It would be if it were scoring prose on general quality. It's checking one output against an external document — the written standard is the ground truth, not the model. I keep it boolean rather than scored, I grade named dimensions separately rather than asking for one holistic score, I deliberately refused an "uncertain" verdict because models use it to avoid committing, and there's a human gate downstream that continuously samples whether the judge is being too lenient.

Judge bias is real and documented — position, verbosity, self-preference. Most of that literature concerns comparing two candidate outputs to each other. Comparing one output to a fixed rubric is a different and smaller failure surface.

Because a platform's constraint is capacity, not ideas

Cost as a product decision

Normal software costs the same whether one person uses it or a million. These don't. Someone has to own the cost per unit of value, and that someone is the product owner.

3 axesseparate caps for text, retrieval and image generation — one shared budget lets any axis silently drain the others
44%saved by routing the expensive model only to the surface people actually look at
25%saved by not re-buying information already owned — an archive checked before any paid retrieval
15% → 0timeout rate on long calls, fixed by streaming: same tokens billed, same wall-clock, one line of code

Three things this taught me that transfer directly

  • Caps are policy, not just safety. Raising a cap until it stops firing removes the signal that you're spending more than designed. Pair the cap with a salvage path — finish and flag rather than losing the run — and you keep the signal and the work.
  • Report on the axis that can move. When one number spikes 30% you should know immediately which stage to open, not spend a day narrowing it down.
  • A caching or routing standard belongs at the platform layer, not in each application. Set it once behind a gateway and every team inherits it without changing their code. That's the difference between optimising an app and being a platform.

Containment

Guardrails, and the risk I'd name before being asked

You can ask a model nicely not to do something, or you can arrange things so it can't. Only the second one is a control.

LayerWhat it doesIn the pipeline
OutputValidate before anything is shown or sentSanitisation before publish; schema validation on every structured step
Tool scopeLimit what the system can do at allA single scoped tool is the only send path — the model cannot notify arbitrarily
DeploymentInherit the firm's controls rather than reinvent themHosted on the internal self-service platform, behind enterprise MFA
InputTreat ingested content as data, never instructionNot built. See below.

The gap I'd close first

Indirect prompt injection. These steps read pages and ticket descriptions written by other people, then generate customer-facing documentation and send a notification. Anyone who can write a ticket description can put text in front of a model that also has a send capability. There was no input guardrail against that.

Two things limited the blast radius by architecture rather than by intent: the human gate on the path to anything customer-facing, and the fact that the only send path is one narrowly scoped tool. Those are two of the four real mitigations. The others — structurally separating fetched content from instructions, and filtering output for exfiltration — are what I'd add, alongside logging attempts so it becomes a detection signal rather than a silently blocked request.

No prompt-level defence is complete. That's precisely why the containment has to be architectural.

Why this matters for a central platform

The column on the left is what a team gets when it builds inside an organisation that already has controls. The column on the right is what a team has to build for itself when nobody else will catch its mistakes. A central AI platform's job is to make the right-hand column something spoke teams inherit rather than rebuild — an eval harness, a cost standard, a trace format, a routing rule — so that shipping responsibly is the cheap path rather than the disciplined one.

That's the same argument as the five gates, one level down: gates decide what should be built, this decides what every build gets for free.
